# 版本规划

每个版本均可独立运行并具备实际可用性，不是最后才可用。任务详情见 [TASKS.md](TASKS.md)。

## V0.1 项目骨架与空壳应用

- 目标：验证 Tauri + Vue3 + TS 技术栈打通
- 功能：可运行的空 Tauri 窗口，基础菜单/按钮触发"打开文件夹"系统对话框并显示路径
- 原因：先打通最基础的技术链路和项目骨架规范，作为所有后续模块的地基
- 效果：能启动窗口、能选择一个文件夹
- 验收标准：启动时间 < 1 秒；空闲内存 < 100MB；选择文件夹后路径正确显示
- 可独立发布：技术验证性质，不建议对外，仅内部里程碑

## V0.2 文件树与纯文本编辑

- 目标：具备真正的文件读写编辑能力
- 功能：侧边栏文件树、CodeMirror6 接入（先不做 markdown 渲染）、多标签、Ctrl+S 保存、未保存状态提示、关闭未保存文件确认弹窗
- 原因：先把"文件系统+编辑器状态管理"这个最容易踩坑的地基打牢，不掺杂 markdown 渲染复杂度分散风险
- 效果：可当作一个轻量纯文本编辑器日常使用
- 验收标准：UTF-8 含中文文件读写无损；多标签切换不丢失未保存内容；关闭未保存文件有确认
- 可独立发布：可以，等价于一个精简文本编辑器

## V0.3 Markdown Live Preview（核心体验，风险最高，优先做）

- 目标：实现 Typora 式渐进渲染
- 功能：`@lezer/markdown`（含 GFM）解析接入；标题/粗斜体/删除线/行内代码/列表/任务列表/引用/分割线/代码块高亮/链接的 Decoration 渲染；大文件性能基准测试与优化
- 原因：这是产品核心差异化体验，也是技术风险最高的部分（Decoration 系统的正确性与性能），必须尽早验证，避免后期发现问题被迫推倒重构
- 效果：打开 .md 文件即获得接近 Typora 的渲染效果，光标进入显示原始语法、离开恢复渲染
- 验收标准：20000 行文档滚动帧时间 < 16ms；核心语法渲染正确；保存后文件内容与磁盘一致无格式破坏
- 可独立发布：可以，此时已是一个可日常使用的"Typora 平替"最小版本

## V0.4 图片与资源管理

- 目标：支持图片插入与本地资源管理
- 功能：图片 Widget 渲染（懒加载）；粘贴图片自动保存到 assets 目录并插入语法；拖拽图片文件插入
- 原因：图片是笔记高频需求，且是文件系统能力的自然延伸，依赖 V0.2 文件系统与 V0.3 渲染能力已就位
- 效果：截图后 Ctrl+V 直接插入图片，无需手动管理路径
- 验收标准：粘贴/拖拽图片后生成正确的相对路径引用；大量图片文档滚动不卡顿
- 可独立发布：可以

## V0.5 可视化 Git 面板（重点功能）

- 目标：内建完整的日常 Git 操作面板
- 功能：仓库状态检测；改动文件列表（未跟踪/已修改/已暂存分类）；diff 查看器；暂存/提交；commit 历史列表与详情查看；分支查看与切换（联动刷新文件树与编辑器）
- 原因：明确的重点需求，且此时文件编辑核心已稳定，是引入版本历史价值最大的时机
- 效果：日常"编辑-查看改动-提交"全流程无需切出到外部 Git 客户端或命令行
- 验收标准：状态/diff/历史数据与命令行 git 结果一致；分支切换后 UI 状态无脏读
- 可独立发布：可以，此时已是完整可用的"笔记编辑+版本管理"闭环产品，是 MVP 的完成点

**MVP 边界：V0.1~V0.5 完成即达成 [PRODUCT.md](PRODUCT.md) 中定义的 MVP 能力清单。**

## V0.6 设置系统与主题（MVP 之后）

- 目标：个性化与配置持久化
- 功能：设置面板、本地配置持久化、明暗主题切换、编辑器字体字号设置
- 原因：核心功能完备后补齐长期个人使用的体验细节
- 验收标准：设置修改立即生效并重启保留；主题切换无需重启
- 可独立发布：可以

## V0.7 命令面板与快捷键系统

- 目标：建立"命令"这一层架构抽象，为后续扩展打基础
- 功能：Command 注册中心、快捷键绑定、模糊搜索命令面板；已有功能（保存/打开/commit 等）迁移为 Command 调用
- 原因：故意安排在核心功能之后——此时已有足够多"真实命令"可以指导抽象设计，避免过早设计导致后期推倒重构
- 验收标准：所有已有操作可通过命令面板搜索触发，快捷键可自定义
- 可独立发布：可以

## V0.8 PDF/HTML 导出

- 目标：内容对外输出能力
- 功能：markdown-it 一次性渲染完整 HTML；调用系统打印能力导出 PDF；导出 HTML（内嵌样式）
- 原因：输出分享是常见诉求，此时核心体验已稳定，适合叠加"变现"到其他格式的能力
- 验收标准：导出效果与编辑器内渲染基本一致（中文字体/代码高亮/表格/图片正常）
- 可独立发布：可以

## V0.9 全文搜索

- 目标：多文档场景下的检索能力
- 功能：单文件内搜索替换、跨文件（文件夹范围）搜索、搜索结果面板与跳转
- 原因：文档数量增多后是刚需，此时 UI 布局（侧边栏/面板体系）已经成熟，可直接叠加
- 验收标准：搜索结果准确并可跳转定位；替换不破坏原有格式
- 可独立发布：可以

## V1.0 打磨与扩展点预留

- 目标：稳定性收尾，面向长期使用
- 功能：性能复盘优化；异常处理完善；Editor/FileSystem/Command 等模块公共接口稳定化（为未来插件系统铺路）；Mac 构建链路验证
- 原因：确保架构经得起长期迭代，为下一步真正的插件系统/完整 Mac 支持做准备
- 验收标准：核心场景无阻塞 bug；Windows 端启动时间/内存/包体积达到既定指标
- 可独立发布：是，即正式 1.0

## 推荐开发顺序与理由

顺序即 V0.1→V1.0：先地基（项目骨架+文件系统，V0.1-V0.2）→ 尽早验证技术风险最高且最核心差异化的 Live Preview 体验（V0.3）→ 高频实用功能（图片，V0.4）→ 用户明确要求的重点功能（Git 面板，V0.5，需要前面文件系统稳定后接入）→ 体验打磨（设置，V0.6）→ 架构抽象收敛（命令面板，V0.7，故意安排在核心功能之后，因为此时已有足够真实命令场景指导抽象设计，避免过早抽象导致后期推倒重构）→ 产出型功能（导出/搜索，V0.8-V0.9，属于"有内容才有意义"的能力）→ 整体打磨到 1.0。

核心逻辑：风险最高、最核心差异化的部分最先验证；架构抽象类工作（Command 模块）延后到有真实场景支撑再做，直接回应"新增功能不能推倒重构"的硬性要求。
